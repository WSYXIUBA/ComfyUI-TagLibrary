# 挑选器「手动/半手动」可用性重构设计案

> 日期：2026-09-20  
> 触发：用户实测反馈「想手动挑道具姿势，压根没有标签栏；武器的支持都在武器档案里，**只可编辑，不可选**」  
> 方法：huashu-chrome 接管用户浏览器，**真实点击**逐页走查 + 数据模型量化  
> 结论：这不是样式问题，是**产品定位问题** —— 挑选器是按自动模式建的，手动/半手动没有一等公民的位置

---

## 1. 根因：两个互不相通的世界

```
┌─ 标签世界 ─────────────────────┐   ┌─ 档案世界 ────────────────────┐
│ 4743 个扁平标签                 │   │ 18 档案 × 75 束                │
│ 轴 → 槽位 → 标签                │   │ 束 = {出词, 手数, 视线,         │
│ 无结构、无约束                  │   │        状态槽, 互斥, 蕴含, NL}  │
│                                 │   │                               │
│ ✅ 可在「挑标签」浏览/点选       │   │ ✅ 引擎自动加成时使用            │
│ ❌ 表达不了"占几只手/会冲突"     │   │ ❌ 只能在「武器档案」编辑        │
└─────────────────────────────────┘   └───────────────────────────────┘
             ▲                                      ▲
       手动用户在这里                         自动引擎在这里
             └──────────── 中间没有桥 ─────────────┘
```

**为什么会长成这样**（不是谁偷懒）：引擎的束系统需要 `hands`（手数账本）/`gaze`（视线）/  
`state_slot`（状态槽）/`conflicts_with`（互斥）这些**扁平标签表达不了的结构**，  
所以档案层做成了引擎内部结构；它的 UI 自然就成了**维护工具**，而不是**使用入口**。  
手动用户于是被锁在门外。

### 七个页面的定位失衡（这是"往大了想"的关键）

| 页面           | 定位          | 手动用户能用吗                    |
| ------------ | ----------- | -------------------------- |
| 🏠 首页（拼接流水线） | 导览          | ⚠️ 只是看图，不能操作               |
| 挑标签          | **使用**      | ✅ 唯一的挑选入口                  |
| ⚔ 武器档案       | 维护/编辑       | ❌ 只编辑                      |
| 🧬 互斥域       | 维护/编辑       | ❌ 只编辑（但手动挑选时**恰恰最需要看到冲突**） |
| ✍ NL 句式      | 维护/编辑       | ❌ 只编辑                      |
| 📦 预设        | 维护/编辑（也能套用） | ⚠️ 半可用                     |
| ⚙ 设置         | 配置          | —                          |

**7 个页面里 5 个是"编辑/配置"面，只有 1 个是"使用"面。**  
自动模式下用户不需要操作档案（引擎自己挑），所以这个失衡没暴露；  
手动模式一进来就撞墙。

## 2. 四个方案（从最小改动到最彻底）

### 方案 A：把档案词"摊平"进挑标签索引

把 `profiles` 的 tags / poses / extras 词注入挑标签的搜索与槽位，做成虚拟槽位「武器姿势」。

|   |                                                                  |
| - | ---------------------------------------------------------------- |
| ✅ | 改动最小（后端加一层合并 + 前端零改）；立刻解决"搜不到"                                   |
| ❌ | **丢掉结构**：手选了 `holding gun` 却不知道它占 1 只手、会和 `looking at viewer` 冲突 |
| ❌ | 与档案引擎的自动加成**双轨**：手动选的词不经束账本，hand 数会算错                            |
| ❌ | 越修越乱：4743 → 4795 个扁平词，用户更难找                                      |

**判定：❌ 不推荐。** 它把结构化数据降级成扁平词，等于承认结构没用。

---

### 方案 B：档案升格为「一等可选对象」（挑标签里长出选择器）★推荐骨架

**核心思想**：档案不是编辑器里的数据，而是**可挑选的成品组合**。

挑标签页对「道具武器 / 武器装备」这类**挂载槽位**渲染两层：

```
第 1 层：武器本体        [ 武士刀 ]  [ 剑 ]  [ 大剑 ]  [ 枪械 ]  [ 弓 ] …   ← 现成的 53 个武器标签
                          ↓ 选中"武士刀"后，第 2 层就地展开
第 2 层：该档案的姿势     ○ 拔刀   ○ 双手持刀   ● 单手持刀   ○ 反手握持     ← 单选
                          ↓ 点"单手持刀"
结果：一次性纳入 { holding sword } + 手数 1 + 视线 0 + 状态槽 weapon_state=drawn
```

关键性质：

- 手动选的**走的还是同一套束**，所以 `hands`/`gaze`/`state_slot` 照旧生效 → **不与引擎双轨**
- 自动与手动**共用同一份数据**，不会漂移
- 武器档案页保持"编辑"定位不变，但**每条束标题旁加一个「➕ 加到面板」** → 从编辑页也能用

**控件语义**（遵用户铁律：开关→开关、多档→分段、一次选择→下拉、动作→按钮）：

- 武器本体：点选 chip（可多选，双手各一把）
- 姿势束：**单选**（同一武器同时只有一个持握姿势）→ 用 radio 形态或分段按钮
- 已选：chip + ✕

|    |                                     |
| -- | ----------------------------------- |
| ✅  | 结构不丢，自动/手动同源                        |
| ✅  | 直接解决 29 个词"选不到"                     |
| ✅  | 改动面可控：后端暴露一份"档案→可选束"的只读接口；前端挑标签页加一层 |
| ⚠️ | 需要新增一个 API（只读）+ 挑标签渲染分支             |

---

### 方案 C：档案实例变成面板上的「复合 chip」（B 的增强）

在 B 基础上，把"档案实例"做成节点面板的一等公民：

```
面板上出现：  [ ⚔ 武士刀 · 单手持刀 ✕ ]     ← 点一下可以换姿势，不换武器
              [ ☕ 茶杯 · 双手捧 ✕ ]        ← 支持多个道具（左手杯、右手枪）
```

- 换姿势时自动重算 hands / gaze / state_slot，**当场**与面板其余词做互斥检查
- 因为 `hands` 账本是 2，面板要能看见**余量**（"手：1/2 已用"）

|    |                                      |
| -- | ------------------------------------ |
| ✅  | 真正匹配"半手动"的真实工作流：先手挑主体 → 再手挑道具 → 引擎补空 |
| ✅  | 复合 chip 让"武器+姿势"成为一个可整体操作的对象，符合心智    |
| ⚠️ | 需要面板渲染改一处 + hands 余量可视化              |

---

### 方案 D：把「约束」搬到挑选现场（跨方案的共性必需项）

不管选 B 还是 C，手动挑选时**看不到约束**这件事必须解决：

| 现状                                | 应该                             |
| --------------------------------- | ------------------------------ |
| 选了 `holding gun` 不知道占几只手          | 当场显示"手 +1（剩 1）"                |
| 选了互斥词等到生成时才 `dropped`             | 当场变灰 + 提示"与 ✅holding sword 冲突" |
| 选武器时不知道会不会和 `looking at viewer` 撞 | 视线被占时相关词变灰                     |

**实现前提**：把 `engine.tag_ok`（`engine.py:287-304`）抽成**纯函数谓词**，暴露给前端复用。  
这正是架构审查报告里 **N4「两套闸门」** 那条 —— 手动路径现在根本不走引擎的  
`minor_lock`/`gender_lock`，所以手动钉选未成年词 + 露骨词时引擎拦、手动不拦。  
**修 N4 与做 D 是同一件事。**

### 推荐组合：**B（骨架） + D（伴随必需）→ 再上 C**

- **B 先做**：一次性打通"手动选档案"，价值最大、风险最低
- **D 同期做**：不做 D，B 选出来的词用户仍然看不懂后果；且 D 顺带修掉 N4 合规漏洞
- **C 后做**：等 B/D 稳住，再把复合 chip 做进面板

## 4. 交互逻辑草案（以「手动挑武士刀 + 反手握持」为例）

```
① 打开挑选器 → 挑标签页
   搜索框输入 "katana"        → 命中 [武士刀 katana] （武器本体，可选中）
   或 左栏点 道具武器 ▸ 武器装备 → 53 个武器标签里挑

② 点击 [武士刀] → 该 chip 变为已选态
   下方就地长出「持握姿势」单选组（数据来自 weapon.katana.poses）
        ○ 拔刀 drawing sword
        ○ 双手持刀 two-handed sword, holding weapon two-handed
        ○ 单手持刀 holding sword
        ○ 反手握持 reverse grip, holding sword
   ⚠ 默认不预选任何姿势（避免替用户做决定）

③ 点「反手握持」
   当场反馈：  手 +1（余 1）  ·  状态 weapon_state=drawn
   同时变灰的词：sheathed sword / katana on back / scabbard（来自 conflicts_with）

④ 底部「已挑选」区出现两条：
        [ katana ✕ ]  [ reverse grip ✕ ]      ← 束的出词逐条可单独移除
   ⚠ 移除姿势时，其抢用的手数/状态槽要一起释放

⑤ 点「✓ 确定并保存」→ 回节点面板
   面板上出现复合 chip：  [ ⚔ 武士刀 · 反手握持 ✕ ]
   点它 → 换姿势（不换武器）；点 ✕ → 整体移除

⑥ 若用户改主意想换成"枪械"
   直接点 [枪械] → 弹出"换武器将替换姿势：单手持刀/垂手持枪/背枪…"
   （破坏性操作给一次确认，不做静默替换）
```

```
        未在标签库找到。它属于「枪械」档案的姿势词。
        [ 去 ⚔ 武器档案 用这个姿势 ]   ← 一键跳到该档案并定位到该束
```

## 5. 走查中新发现的问题（你说"还有等等"，这是我主动找的）

### 5.1 已实测确认

1. **可访问名是"指令"而不是"对象名"**：左侧轴开关的 5 个 checkbox 可访问名**全是「点击关闭整条轴」**  
   → 读屏用户分不清哪个是哪条轴。应改为轴名（"画质规格"），把提示挪到 `title`。
2. **武器档案页的数字框可访问名全是「自动配额」**（手数/视线/权重三个都叫这个）  
   → 同样读屏不可用，且视觉上用户也不知道哪个是手数。应改为「手数」/「视线」/「权重」。
3. **搜索空态是死路**（见 §4）。
4. **术语"束"**：档案页满屏"束"，用户不懂。可改「姿势/持握方式」（内部 id 不变）。

### 5.2 我判断存在、需你确认的问题（你可能没想到的）

1. **手动模式下「总词数 40~60」还生效吗？** 面板上那个「自动配额 40~60」是给自动模式的。  
   手动挑 3 个词，是出 3 个还是被补到 40 个？**界面没说**，这是"改完看不到变化"的又一来源。
2. **手动挑的词能设权重吗？** 挑标签里点选的词默认权重 1.0，用户想写 `(katana:1.2)`  
   只能去节点面板的预览里手改或改词库默认权重。**手动用户缺一个"给这个词调权"的入口。**
3. **挑进来的词落在哪个输出段位，用户看不见。** Anima 有优先级次序（画质→人数→…），  
   手动挑的词顺序如何？挑标签里没有"段位"提示。
4. **多道具并存时的 hands 冲突**：一手枪一手杯 = 2 手用满，此时再选"双手持剑"应被拦。  
   现在没有这个检查（手动路径不走引擎闸门，见 N4）。
5. **已挑选区缺批量操作**：挑了 30 个想全清/按轴清，只能一个个 ✕。（已知面板有"清空标签"，  
   但那是清节点面板的，不是清挑选器的 `picked`。）
6. **键盘不可达**：98 个 chip 只能鼠标点，Tab 走一遍要 98 次。缺 `/` 聚焦搜索、  
   方向键在 chip 间移动、Enter 选中的键盘路径。
7. **互斥域页与挑选现场脱节**：用户想"让这两个词别同时出现"，得去互斥域页手写成员，
   而**在挑选现场看见冲突时却没有任何"就地加规则"的入口**。
   → **v1.10.0 已落地**：已挑选区每个词后加 `⟂`，点 A 的 ⟂ 再点 B 的 ⟂ 即写规则
   （`addMutexRule()`；只回写主文件那份，`ext.*` 不落主文件）。

## 8. 决策与实施记录（2026-09-20 16:34 用户拍板）

### 用户的三条决策

| # | 决策                                                     | 落地含义                     |
| - | ------------------------------------------------------ | ------------------------ |
| 1 | 按最优来 → **B + D**                                       | 档案升级为可选项 + 约束现场化         |

### ⚠ 对决策 3 的一处技术修正（已与用户确认方向）

"不受规则约束"必须分两类处理：

### 10.2 实机抓到并修掉的两个缺陷（都是本轮新代码自己的）

1. **手数按词累加会翻倍** —— 一个姿势常出 2 个词（`two-handed sword` +
   `holding weapon two-handed`），按词求和把「双手持刀」算成 4 只手（实机显示
   `手 4/2`）。改为**按姿势束计一次**，修后同一场景显示 `手 3/2`（2+1，正确）。
2. **跨档案共享词被「让位」误删** —— 点枪械的单手持枪时，`togglePose` 会清掉该档案
   其它姿势的词，而 `holding weapon two-handed` 同时属于武士刀的「双手持刀」，
   于是**武士刀那束从 2 个词变 1 个**。修法：让位时跳过「别的档案束已占用的共享词」，
   并把用户先前手点进来的散词归入本束。修后同一操作两束都是 2 个词。
   ⚠ 残留口径：若某词已被 A 档案的束占用，B 档案那条只用该词的姿势在 B 侧显示为
   「已选」但不会把词搬过去（一个词在 state 里只能属于一束）。属数据模型限制，已记录。
