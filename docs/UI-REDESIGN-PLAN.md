## 0. 先给判断

你的三个直觉都是对的，而且都能被证据支撑：

| 你的判断 | 核查结果 |
|---|---|
| 分类逻辑（二级树）不适合提示词 | **成立**。9 个大类里 **7 个恰好等于 1 条轴**，唯一例外「人物主体」一个类跨了 5 条轴（1381 词）。大类这一级在 8/9 的情况下与轴完全冗余，只在最该细分的地方塌成一锅 |
| 有的面板多余 | **成立**。核实出一处**死 UI**（Fast/Smart 切换）和一组**概念重复**（互斥域 vs 防冲突关系） |
| 有的只给看不给改 | **成立**。武器档案 / 互斥域 / NL 句式 三个页签的结构完全一样：只读卡片 + 一个 JSON 文本框，**除 JSON 外无任何行内编辑** |

核心结论：**分类逻辑不需要"重建"，只需要"重新挂父级"** —— 迁移 100% 机械、零冲突（见 §2.2）。
真正需要重写的是 **UI 的信息架构**。

## 1. 现状诊断

### 1.1 分类逻辑：大类与轴系统性错位（数据证据）

现有 9 大类 → 12 轴的实测映射：

```
画质规格   2 子类  ->  1 条轴   meta 85
人物主体  19 子类  ->  5 条轴   count 38 / character 106 / appearance 934 / clothing 38 / prop 265   ← 病灶
服装系统  12 子类  ->  1 条轴   clothing 848
姿势动作   7 子类  ->  1 条轴   action 397
构图镜头   4 子类  ->  1 条轴   camera 186
光影氛围   4 子类  ->  1 条轴   lighting 235
场景环境  10 子类  ->  1 条轴   environment 619
风格媒介   5 子类  ->  1 条轴   style 361
材质特效   2 子类  ->  1 条轴   material 245
```

**读法**：8 个大类就是 8 条轴换了个名字；只有「人物主体」是真正的"主题归类"，
把人数、年龄、物种、发色、表情、裸露、武器、食物全塞在一起 —— 它跨了 5 条轴。

**这就是"二级树不适合提示词"的本质**：
- 树的第一级（大类）是**作者视角**（这个词是讲什么的），
- 轴是**生成视角**（这个词在 prompt 里放哪个槽位）。
- 系统真正的骨架是轴（`axes.py` 注释原话："分类树降级为 UI 视图"），
  但存储、CRUD、导入导出、排除配置**全部围绕树**。于是每个词有两套坐标，
  悬停提示「轴: X · 树: Y/Z」就是这种双重身份被迫暴露给用户的样子。

### 1.2 UI：8 个页签把三类不同频率的任务平铺在一起

挑选器现有 8 页签，但它们的**使用频率差一个数量级**：

| 页签 | 任务性质 | 频率 |
|---|---|---|
| 挑标签 | 选词 | **每次出图** |
| ⚙ 设置 | 调参数 | 偶尔 |
| 🚫 排除类目 | 调范围 | 偶尔 |
| ⚔ 武器档案 / 🧬 互斥域 / ✍ NL 句式 | **维护数据** | 几乎不做 |
| 🏷 标签库管理 | **维护数据** | 几乎不做 |
| 🧷 防冲突关系 | **维护数据** | 几乎不做 |

后果有两层：
1. **高频任务被低频任务挤压** —— 用户每次选词都要先跨过 7 个陌生页签；
2. **低频任务因为"顺路塞进来"而做得很潦草** —— 6 个数据类页签全挤在一个 1200px 弹窗里，
   只能做成"只读卡片 + JSON 兜底"，这正是"只给看不给改"的成因。

### 1.3 具体的冗余与死 UI（逐条证据）

**① Fast/Smart 引擎切换是死 UI（建议直接删）**

```
settings 里的键: []                    ← random_configs 根本不存在
resolve_config(random_config_ref=default_fast)  = {total_min:None, total_max:None, bundle_pose_prob:0.85, extra_prob:0.35}
resolve_config(random_config_ref=default_smart) = {total_min:None, total_max:None, bundle_pose_prob:0.85, extra_prob:0.35}
```

两个值**完全相同**。1.3.0 已把双引擎合并为单一结构引擎（CHANGELOG 明写 `random_engine.py`/`rules_engine.py` 退役删除），
但节点面板上的 Fast/Smart 切换按钮残留至今，点了没有任何效果。

**② 互斥域 vs 防冲突关系 = 同一个概念的两个页签**

```
grouprules.json : 50 组（组内成员 2~133 词，同域任意两词互斥）
conflicts.json  : 33 条规则，左侧->右侧类型分布：
                  tags->tag  15 条   ← 这 15 条本质就是"域"（一组词互相排斥）
                  sub->sub    9 条
                  tags->sub   7 条
                  tags->cat   2 条
```

两者语义完全相同（都是"两两互斥"），只是表达方式不同：一个是"域成员表"，一个是"A ⟂ {B,C}"。
**用户视角却是两个页签**，还得自己判断该去哪个页签加一条互斥。

**③ 三个数据页签 = 同一套代码写三遍**

```
⚔ 武器档案 : 顶层键 [version, profiles]
🧬 互斥域   : 顶层键 [version, groups]
✍ NL 句式   : 顶层键 [version, doc, words, families, pose_map, sub_family, obj_kind, env, light, intro]
```

三者的 UI 结构**完全一致**：列表卡片 + `<details>` JSON 文本框 + 保存按钮
（共用 `editorFoot()` 函数）。差别只在渲染的字段。
→ 这是"功能可以共用一套面板"的确证，但现状是三份独立的渲染代码 + 各自的 JSON 兜底。

**④ 设置分散在三处，同一批值三处能改**

- ComfyUI 原生设置面板（插件注册了 6 个 setting）
- 挑选器 ⚙ 设置页（36 个控件）
- 管理页（`one_way_delete` 等）
且 ⚙ 设置页内部把**三种不同层级**的东西混在一个列表里：
节点级参数（分隔符/权重语法/去重）、引擎级参数（NL 开关/带束概率/武器上限）、
全局偏好（默认模式/UI 比例/显示语言）。

**⑤ 管理页有两个入口**

「🏷 标签库管理」页签是 **iframe 嵌管理页**，而管理页本身也能独立打开（顶栏 🏷 按钮 / `/taglib`）。
同一页面两条路径进来，会出现"挑选器底栏 + 管理页顶栏"两层操作栏叠在一起。

**⑥ 布局逻辑的具体毛病**

- 挑选器 `.tp-cols` 永远是「200px 侧栏 + 内容区」，但只有 2/8 个页签用得上侧栏 →
  其余 6 个页签左边一大条空白，视觉重心偏右。
- 「挑标签」页签内部还有一套「🌲分类树 / 🎯拼装轴」切换 → 与顶栏 8 页签构成**两层导航**，
  且这个切换的存在本身就是 1.1 那个双重身份的补丁。
- 抽取范围控件（总控制 + 每子类 min~max 输入框）被挤在左侧栏的树节点里，
  每个子类一行两个数字输入框，密集且容易误点。

### 1.4 具体的缺失

| 缺失 | 说明 |
|---|---|
| 数据不能行内编辑 | 档案的姿势表、互斥域成员、NL 句式族，全部只能整体改 JSON |
| 改完不能局部验证 | 只能"保存后才生效"，没有单条预览/dry-run |
| 关系不可发现 | 某个标签属于哪些互斥域？档案间有何共享词？只能靠 grep JSON |
| 无变更历史 | 保存直接覆盖（仅留 `.bak`），改错了只能整文件回滚 |

### 1.5 与目标模型（Anima）和母数据集（Danbooru）的对齐缺口

> 本节依据外部一手资料核对，非推测。来源见文末「参考依据」。

**Anima 作者明确规定了 tag order**（三处独立来源一致，含模型页与第三方教程）：

```
[quality / meta / year / safety + style slot] [1girl/1boy/1other] [character] [series] [artist @] [general tags]
「每段内部顺序无所谓」
```

推荐正向前缀 `masterpiece, best quality, score_7, safe,`；
推荐负向 `worst quality, low quality, score_1, score_2, score_3, artist name, blurry, jpeg artifacts, chromatic aberration`。
另外：style slot 是**关键控制点**（"换它就能换整体风格，其他不动"）；artist 必须带 `@` 前缀，否则效果很弱；
权重需要比 SDXL 更高（`(chibi:2)`）；模型经过随机 tag dropout，不需要把所有相关词都写。

**Danbooru（母数据集）自己的标签体系**：只有 **5 个 category** ——
`general(0) / artist(1) / copyright(3) / character(4) / meta(5)`，
另有约 **100 个 Tag Group** 用来做内容主题分组
（`hair styles` / `eyes tags` / `attire` / `posture` / `image composition` / `lighting` / `locations` / …）。

**据此逐段核对库内覆盖，缺口如下**：

| Anima 段落 | 库内覆盖 | 缺口 |
|---|---|---|
| quality · human-score | 2 词（masterpiece / best quality） | 缺 good / normal / low / worst quality |
| quality · aesthetic `score_*` | **0 词** | **完全缺失**（Anima 主推的评分体系） |
| year / 时间段 | 0 / 1 词 | **基本缺失** |
| meta（highres / absurdres / anime screenshot / jpeg artifacts） | 3 / 5 词 | 缺 2 |
| safety（safe / sensitive / nsfw / explicit） | 1 词，且只是布尔开关 | 缺 3，且**不可抽** |
| 1girl / 1boy / 1other | 38 词 ✓ | 齐 |
| character | 106 词（年龄/种族） | 缺"具名角色"概念 |
| **series / copyright** | **0 词** | **完全缺失** |
| **artist（含 `@` 语法）** | **0 词**，且无 `@` 输出规则 | **完全缺失** |
| **负向提示词** | **无任何负向轴/词表** | **完全缺失**（Anima 强需求，且 Danbooru 官方有 Flaws/Quality 组） |
| style slot | 风格媒介 5 槽位 361 词 | 有词，但**没被当作关键控件** |

**两个被这次核对推翻/提升的判断**：

1. **轴的输出次序错了**。当前 `AXIS_ORDER` 把 `style` 排在**第 11 位（倒数第二）**，
   而 Anima 要求 style 与 quality/meta/year/safety **同在第一段**（最先出现）。
2. **括号消歧不是边缘情况，是官方语法**。Danbooru 规定同名歧义要用 `(qualifier)` 限定
   （`black_rock_shooter` 是作品、`black_rock_shooter_(character)` 是角色）。
   所以 §1.4 与 1.4.1 待办里那条 "`.md` 往返在 zh 含括号时产生畸形标签" 的缺陷
   **优先级应当提高** —— 它破坏的是官方语法的一部分，不是罕见个例。
   同时库内 1.5 词表规范也应照 Danbooru：物体用**单数**、`_` 不能作首尾、标签不得含逗号与星号。


### 1.6 输出质量实测：比"分类错位"严重得多的问题 ⚠️

用群里那条真实提示词当基准，做了两件事：量库的覆盖、量插件实际吐出来的词。
结论是 —— **分类只是表症，真正致命的是"抽取语义"本身错了。**

**（一）覆盖率：群里的提示词 62 个词，库内只有 34 个（55%）**

且缺失的不是生僻词，而是**最基础的基准词**：

| 缺失 | 库里只有 | 后果 |
|---|---|---|
| `breasts` | `huge/small/perky/large breasts` | 表达不了"普通"，只能抽到带修饰的，且**大/小可能同时出现** |
| `thighs` | `thin/thick thighs` | 同上（粗细可能同时出现） |
| `bow` | `bowtie` | 基础配饰缺失 |
| `stomach` | `flat stomach` | 同上 |
| `black choker` / `white bow` / `black shirt` | —— | **"颜色+物体"复合词整类几乎没收（全库仅 72 个）**，而这类在 Danbooru 极常用 |
| `score_9/8/7`、`very awa`、`very aesthetic`、`ultra-detailed`、`huge filesize`、`detailed pupils` | —— | 质量/细节层词汇整层缺失（见 §1.5） |

**另一个发现：`aliases` 别名机制完全空转** —— 4357 个词的别名字段**全为空**。
Danbooru 官方有 Tag Alias 机制，而这里连 `tights`→`pantyhose` 这类常用同义都没有，
搜索与去重都受影响。

**（二）实际输出：同配置下插件吐出 200~213 个词，而基准是 62 个**

默认 `fill_master` 的语义是"**每个槽位抽 3~5 个**"，63 个槽位 → 189~315 词。
更严重的是**抽出来的词之间毫无一致性**。实测 5 个种子的输出（真实数据）：

| 冲突类型 | 实测例子 |
|---|---|
| 年龄三/四重 | seed101 `toddler` + `middle-aged man` + `elderly man`；seed505 `sixties` + `middle-aged` + `aged up` + `adult male` + `elderly man` |
| 物种/身份四重 | seed101 `pixie` + `wizard` + `halfling` + `knight` |
| 表情多重互斥 | seed101 `embarrassed`+`furious`+`masochistic expression`+`focused expression`；seed303 `grin`+`intense stare`+`bashful`+`giggle`+`calm`+`unconscious` |
| **白天+夜晚同时** | seed101 `daytime` + `starry night sky` + `eclipse night`；seed404 `golden afternoon` + `blood moon night` + `crescent moon night` |
| 天气全叠 | seed101 `snow flurry` + `light snow` + `heat haze` + `fog bank` + `meteor shower` |
| 鞋类 4 双 | seed101 `espadrilles` + `slides` + `high-top sneakers` + `soccer cleats` |
| **人数与内容直接矛盾** | seed101 `1boy` + `faceless **female**` + `maid apron` + `thigh strap`；seed303 `3boys` + `tutu` + `high-waisted panties` |
| 人数词自身矛盾 | seed202 `5girls` + `multiple others`；seed404 `0others`；seed505 `1other(单人(其他))`（含已知畸形词） |
| 风格堆砌 | seed101 `quilling`+`kirigami`+`patent drawing`+`lineart`+`kaiju`+`tokusatsu` 同时出现 |

**（三）根因（三条，都不是分类问题）**

1. **抽取配置的语义错了**：`fill_master_min/max` 是"**每槽位**抽几个"，
   63 槽位相乘直接爆到 200+。而合理的目标是"**总共** 40~60 个词"（基准提示词 62 个）。
2. **缺少"单选维度"概念**：年龄、情绪、表情、天气、时间、鞋类、取景、视角……
   这些**天然只能选一个**（或一个子集），但引擎把它们当普通池子，一抽就是 3~5 个。
   这正是 §2.6 类型 3/4 的后果 —— **比"归类不对"更致命，因为直接产出矛盾 prompt**。
3. **没有整体预算与配比**：不同维度的合理数量差一个数量级（风格 1~2 个、鞋 1 个、外貌可 5~8 个），
   而现在所有槽位共用同一个 min/max。

**（四）结论：修复顺序要改**

原分期把"分类迁移"放最前。但实测表明：**分类再对，只要抽取语义还是"每槽位抽 3~5 个"，
输出依然是 200 个互相矛盾的词。** 所以：

> **必须先修"输出质量"（抽取语义 + 单选维度 + 总量预算），再动分类。**
> 前者是"出词能不能用"，后者是"词放得整不整齐"。

**（五）质量验收标准（可量化，作为 §8 重度测试的判据）**

| 指标 | 现状 | 目标 |
|---|---|---|
| 输出词数 | 200~213 | **40~65**（对齐基准 62） |
| 同维度互斥词共现 | 每轮都有（年龄/表情/天气/时间/鞋） | **0** |
| 人数与性别/内容矛盾 | 有（`1boy` + female 专属词） | **0** |
| 质量/元词体系 | 自造堆砌，无 `score_*` | 对齐 Anima 官方（`score_7` + `masterpiece, best quality` …） |
| 角色/作品配对 | 无（库里没有 character/series） | `角色 (作品), 作品` 成对出现 |
| 词表基础覆盖 | 群内基准 55% | **≥95%** |
| 别名机制 | 0 条 | 常用同义/旧名有别名 |

## 2. 分类逻辑重设计

> §1.5 的核对结果改变了这一章的结论：不是"把树改成轴"这么简单，而是**四种不同的语义被压进了一个层次**。

### 2.1 四维分离：一个层次压不下四种语义

原方案（含本文初稿）把「轴 → 槽位 → 标签」当成唯一骨架，把实体当作例外挂上去。
但对照 Anima 与 Danbooru 后可以看出，这里有**四个互相独立、必须分开表达的维度**：

| 维度 | 回答的问题 | 对齐对象 | 数据形态 |
|---|---|---|---|
| **D · 输出次序** | 这个词放在 prompt 的哪一段 | Anima 官方 tag order（6 段） | 有序段位 |
| **B · 内容主题** | 这个词讲的是什么，怎么分组展示 | Danbooru **Tag Group**（~100 个） | 无序标签组（一个词可属多组） |
| **A · 归属** | 它是不是"身份类"，需不需要特殊语法 | Danbooru **category**（5 个） | 单选枚举 |
| **C · 生成结构** | 抽取时它和谁一起出现、占什么资源 | 本项目自研（Anima 未定义） | 槽位(min/max) + 实体 |

**这就是"很多类目不适合分类"的根源**：一张树只能表达一个层次，
于是四个维度被强行叠加 → 武器在 A 维度是 general、在 B 维度属 `weapons`、在 C 维度是实体、
在 D 维度落在 general 段 —— 四种身份无法用"某个大类下的某个子类"表达。

**修正后的目标模型**：

```
A 归属 (5 类, 单选)        general / character / copyright / artist / meta
B 主题组 (多对多)          hair styles · attire · posture · image composition · …
C 生成结构                 槽位(min/max/参与/排除) + 实体(自带束)
D 输出段位 (有序 6 段)      [quality·meta·year·safety·style] [count] [character] [series] [artist] [general]
```

四维各自独立维护，**组合出一个词的完整身份**。
这也解释了为什么"实体"不该是分类：它是 C 维度的概念，跟 A/B/D 无关。

### 2.2 维度 D · 输出次序（对齐 Anima 官方 tag order）

```
第 1 段  quality / meta / year / safety / style slot      ← 全部质量与风格控制，最先出现
第 2 段  count        1girl / 1boy / 1other
第 3 段  character    具名角色（"名字 + from 作品"）
第 4 段  series       copyright / 作品名
第 5 段  artist       @画师名（必须带 @）
第 6 段  general      其余全部（顺序无所谓）
```

要点：
- **style 必须回到第 1 段**（当前 AXIS_ORDER 排在第 11 位是错的）。
- 第 6 段**内部无顺序要求** → 现有的 appearance/clothing/prop/action/environment/lighting/camera/material
  之间的相对次序**不需要精细调**，这反而让迁移更简单（它们只是 general 段内的分组，不是"轴次序"）。
- 第 1 段的 style slot 是"换一个词就换整体观感"的**关键控件**，UI 上应当单独突出，
  而不是混在 361 个风格词里平铺。

### 2.3 维度 B · 内容主题（对齐 Danbooru Tag Group，替代自造"大类"）

Danbooru 官方用 **Tag Group** 做内容主题分组，约 100 个，例如：
`hair styles` / `hair color` / `eyes tags` / `face tags` / `body parts` / `attire` / `dress` /
`legwear` / `headwear` / `neck and neckwear` / `hands` / `posture` / `gestures` /
`image composition` / `lighting` / `locations` / `backgrounds` / `colors` / `food tags` /
`weapons` / `technology` / `nudity` / `year tags` / `metatags` / `subjective` …

关键差异（对比现状自造的 9 大类 63 子类）：
- Tag Group 是**多对多**（一个词可同时属于 `hair styles` 与 `hair color` 相关组），
  而现在的子类路径是**一对一**（一个词只能在一个子类里）→ 这才是"分不进去"的根因之一。
- `image composition` 组同时容纳 **Styles / Techniques（Bokeh·Chromatic aberration·Depth of field…）/
  Flaws（Bad anatomy·Bad hands·Blurry·JPEG artifacts）/ Quality（Watermark·Resized…）/ Background·Color**
  —— 也就是说：**风格、技法、瑕疵、画质在 Danbooru 里本来就同属一个主题组**，
  而现状把它们拆成「风格媒介」「构图镜头」「材质特效」「画质规格」四个大类，切法不一致。
- **Flaws / Quality 组正是负向提示词的词源** → 负向词在母数据集里是一等公民，不是补丁。

### 2.4 维度 A · 归属（对齐 Danbooru category）

| category | 说明 | Anima 段的对应 | 现状 |
|---|---|---|---|
| `general` | 默认，客观描述内容 | 第 6 段（+第2段 count） | 相当于现有绝大部分词 |
| `character` | 具名角色 | 第 3 段 | 缺失（现有"角色身份"是年龄/种族，不是具名角色） |
| `copyright` | 作品 / 系列 | 第 4 段 | **缺失** |
| `artist` | 创作者，输出需 `@` 前缀 | 第 5 段 | **缺失，且无 `@` 规则** |
| `meta` | 系统/元信息（highres·absurdres·tagme） | 第 1 段 | 部分（3/5 词） |

必须落地的两条特殊规则：
- **artist 输出变换**：`kantoku` → `@kantoku`。这意味着**标签不能只是"一个词"**，
  需要"输出变换规则"字段（这也是 1.4.0 里 `_format_tag` 该扩展的地方）。
- **character 与 series 配对**：Anima 明确"先命名角色，再描述外貌"，多角色时尤其重要；
  推荐写法 `hyuuga hinata from boruto: naruto next generations`。
  → character 需要与 copyright 关联（"此角色出自此作品"），这是一条**数据关系**，不是分类。

### 2.5 维度 C · 生成结构：槽位 + 实体

```
旧：  大类(9)  →  子类(63)  →  标签(4357)          + 轴由 axes.py 的路径映射表外部推导
新：  轴(12)   →  槽位(63)  →  标签(4357)          ← 轴就是第一级，不再需要映射表
```

- **轴** = prompt 里的语义槽位，决定输出次序（沿用现有 `AXIS_ORDER`，12 条不变）
- **槽位** = 抽取单位（决定"每个槽抽几个"、"是否参与"、"是否排除"）
- **大类** 降级为**非结构 facet**（见 §7 决策点 1）

### 2.6 维度 C 之延伸：两个一等公民 —— 可枚举属性词 vs 实体

> 这一节回应"武器这类东西不适合用分类来装"的问题。数据实测支持的结论：
> **不是所有东西都该被"分类"，有一类东西是"实体"。**

系统里实际存在两种结构完全不同的东西，但现状把它们都塞进同一棵分类树：

| | **A 类：可枚举属性词** | **B 类：实体（武器 / 物品档案）** |
|---|---|---|
| 结构 | 一个词 = 一个属性值 | 身份词 + 行为束 + 资源消耗 + 状态约束 |
| 占几条轴 | 1 条 | **3 条** |
| 数量关系 | 1 词 1 项 | **1 个实体可含多个身份词** |
| 抽取语义 | 可独立抽出 | 束是原子的：要么整束出生，要么不出生 |
| 例子 | `long hair` / `blonde hair` / `smile` | `katana`（含持握姿势/手数/收刀状态） |

**实测证据**

```
18 份档案的挂载点（现状写成树路径）:
    人物主体/武器装备   7 份
    人物主体/日用道具   7 份
    人物主体/乐器与运动 2 份
    人物主体/食物饮品   2 份

身份词落在 prop 轴，但束成员输出到: action 68 条 / appearance 7 条  → 一个实体横跨 3 条轴
weapon.gun 一个档案含 14 个身份词: gun / pistol / revolver / rifle / … / magic wand
75 条束条目里只有 27 个词在库内 (bundled_only) —— 其余是库外组合词
    (sword out of mouth / holding book / phone to ear …)
「武器装备」槽位里 53 个普通可枚举词与 7 份实体混在一起
```

**关键判断**：束里那 48 个库外组合词**本来就不属于分类树**，是被硬塞进去的。
实体的挂载点至今写成 `人物主体/武器装备` 这种树路径，正是因为模型里缺少"实体"这个位置。

**新模型：两类一等公民并列**

```
轴 (axis) ─── 输出次序（prompt 里的位置），12 条不变
  └ 槽位 (slot) ─── 抽取单位
       └ 标签 (tag)          一个词 = 一个属性值              【A 类·可枚举属性】

实体 (entity)                 自带 schema 的组装单元             【B 类·独立实体】
  ├ 身份词     一个或多个，落 prop 轴
  ├ 行为束     标签 + hands/gaze 资源 + state_slot + 排斥声明
  └ 输出轴     束成员分别落 action / appearance …
```

**抽取时**：槽位池抽 A 类 + 实体独立抽 B 类，两者在**同一个资源账本**
（hands/gaze/状态槽/互斥组）下并行，最后按轴次序**拼接**。

> 这不是推翻 1.3.0 —— `engine.run_auto` 里走到 `mount_of_tag` 就 `attach_bundle()`
> 已经在做这件事了，`bundled_only` / `tags_ext` / `_compile_ext` 就是实体机制的雏形。
> 本方案只是**把这个已隐含承认的区别显式化**，并给它一个正当的位置（而不是挂在树路径下）。

**连带改进**

| 项 | 现状 | 新模型 |
|---|---|---|
| 档案挂载点 | `mount_sub: "人物主体/武器装备"`（树路径） | 声明它占用的**轴/槽位** + 束成员各自声明输出轴 |
| 束成员输出轴 | 硬编码在 `_compile_ext` 里（`"axis": "action"` / `"appearance"`） | 由实体 schema 显式声明 |
| 挑选器 prop 轴 | 普通词与实体 chip 混排，靠 `⚔` 标记区分 | 分两块：「道具词」（可枚举）与「实体」（带束），语义清晰 |
| 工作台导航 | `📚 标签库` / `⚔ 档案`（已平级，但未说明关系） | 明确"实体不是标签库的子集"，两者是不同类型的存储 |
| 未来扩展 | 角色/场景想加约束只能往树里塞特殊词 | 角色包（性别锁+人数约束）、场景包（雨+地面反射+氛围粒子）复用同一套实体 schema |

**六种错配类型 —— "除了武器还有很多"的答案**

用「大类的面积」去衡量，会以为只有武器有问题；按**结构类型**去看，
现有树里有六类东西都不适合用"分类"表达（全部有数据支撑）：

| # | 类型 | 实例 | 为什么归类不行 | 该用什么表达 |
|---|---|---|---|---|
| 1 | **实体** | 武器 / 物品（已有 18 份档案） | 身份词 + 行为束 + 资源 + 状态，**横跨 3 条轴**；1 个档案可含 14 个身份词 | C 维度·实体 |
| 2 | **套装** | 服装套系（校服 / 和服 / 婚纱 = 上装+下装+鞋+袜+配饰） | 13 个服装槽位**各自独立抽** → 会出现"校服上装 + 牛仔裤 + 高跟靴"这种不成套组合 | C 维度·套系束（抽中即成套） |
| 3 | **约束源 / 元信息** | 人数（38 词）、画质词（53+32 词） | 它们不是"候选值"，而是**决定其他抽取**的开关；画质词应固定取前 N，不该随机抽 | C 维度·单选维度 + 固定前缀 |
| 4 | **互斥维度（多选一）** | 风格基线（写实 136 词 ⟂ 二次元）；取景（44 词）；视角（43 词）；环境（340 词）；时间（29 词）；天气（47 词） | 这些是"同一个维度里二选一"，**不是"一组词互相全互斥"**。实测互斥域覆盖面：时间 100%、天气 55%、视角 35%、取景 20%、**风格 1%、环境 3%** —— 风格与环境几乎没被约束住 | C 维度·单选维度（枚举值互斥） |
| 5 | **双人耦合** | 互动与双人（44 词：hugging / carrying / piggyback…） | 抽到"hugging"但人数是 `1girl` 就是矛盾。现在只能靠互斥域碰运气 | C 维度·前提条件（requires count≥2） |
| 6 | **资源声明** | 手部动作（153 词，其中 21 词隐含"持握"）、视线（42 词） | 这些词要和 prop/档案**抢 hands / gaze 资源**，但普通词无法声明"我占几只手" | C 维度·资源占用字段 |

**读法**：类型 1~2 属于"抽取单位错了"，3~4 属于"语义类别错了"，
5~6 属于"缺约束声明"。它们共同指向同一件事 ——
**这四个维度（A 归属 / B 主题 / C 生成结构 / D 段位）必须分开，用一张树压不下**。

### 2.7 要补的缺口清单（外部依据驱动）

按 §1.5 的核对结果，重构时必须一并补齐，否则迁移后仍然跑不出 Anima 推荐的 prompt。

**A 类 · 要新增的段位与词表**

| 项 | 内容 | 依据 |
|---|---|---|
| artist / copyright 段 | 词表 + `@` 输出规则 + "角色 from 作品"配对关系 | Anima 第 3/4/5 段；Danbooru category 1/3 |
| year / 时间段 | `year 2025`、`newest / recent / mid / early / old` | Anima 第 1 段；Danbooru `Tag Group:Year tags` |
| safety 可抽词 | `safe / sensitive / nsfw / explicit` 从布尔升级成可抽词 | Anima 第 1 段 |
| `score_*` 体系 | `score_9…score_1`（注意是 `score_8`，不是 Pony 的 `score_8_up`） | Anima 质量词两套体系之一 |
| quality 补全 | `good / normal / low / worst quality` | Anima |
| meta 补全 | `anime screenshot` / `jpeg artifacts` 等 | Anima 第 1 段 |
| ~~负向提示词轴~~ | **❌ 已排除（用户明确：负面提示词基本不用动，插件只为正面提示词做）** | —— |

**B 类 · 要改的现有行为**

| 项 | 现状 | 应改为 |
|---|---|---|
| style 段位 | `AXIS_ORDER` 第 11 位 | 第 1 段，且作为**独立控件**突出 |
| 权重默认量级 | 沿用 SDXL 习惯 | 提高到 Anima 量级（`(chibi:2)`） |
| 标签数据形态 | 只有 `en / zh / weight` | 增加**输出变换**（artist 加 `@`）与**归属**(category) |
| 主题分组 | 一对一（子类路径） | 多对多（Tag Group） |
| 词表规范校验 | 无 | 照 Danbooru：单数名词、`_` 不首尾、不含逗号与星号 |
| `.md` 含括号 zh 的往返 | 产生畸形标签（已知缺陷） | **必须修** —— `(qualifier)` 是官方语法，不是边缘情况 |
| `aliases` 别名 | 4357 词**全为空** | 补常用同义/旧名（`tights`→`pantyhose` 等） |
| 基准词缺失 | 只有 `small breasts` 没有 `breasts` | 补全"无修饰基准词"，否则无法表达普通状态 |
| 颜色+物体复合词 | 全库仅 72 个 | 按需补（`black choker` 这类在 Danbooru 极常用） |
| 抽取配置语义 | `fill_master` = **每槽位** 3~5 → 200+ 词 | 改为**总量预算** 40~65 + 各维度配比 |

**C 类 · 可借力的官方机制**

| Danbooru 机制 | 本项目对应物 | 可借力之处 |
|---|---|---|
| Tag Alias（别名） | `aliases` 字段 | 已有，可对齐官方别名表 |
| Tag Implication（蕴含） | 尚未实现 | 例：`katana` ⇒ `weapon`；可替代一部分互斥域 |
| Tag Group | 待建主题组（维度 B） | 官方分组可直接作为初始数据导入 |
| Tag Category | 维度 A | 官方 5 类，直接采用 |
| Pool / Pool Group | 无 | 其"合集"概念可参考用于套装（§2.6 六类之类型 2） |

**补齐顺序建议**：A 类里 **artist / copyright / safety / 负向提示词** 四项对出图质量影响最大，优先补；
B 类必须与迁移同时做；C 类按需。

### 2.9 迁移带来的连锁简化

新模型不是"换个组织方式"，它会**消掉一批现有机制**：

| 现有机制 | 新模型下 |
|---|---|
| `axes.SUB_TO_AXIS` 路径映射表（126 行硬编码） | **删除** —— 轴就是父级 |
| `t.axis` 字段（1.4.0 才补的兜底注入） | **删除** —— 不再需要字段，父级即轴 |
| 挑选器「分类树 / 拼装轴」双视图切换 | **删除** —— 只剩一套结构 |
| 每词悬停显示「轴: X · 树: Y/Z」 | **删除** —— 一个坐标就够了 |
| 排除用 `"大类/子类/孙类"` 字符串路径 | 改为**结构化引用**（轴 id + 槽位 id） |
| 抽取范围挤在侧栏树节点里的两个数字框 | 改为抽屉里的**轴/槽位表格**，可整列批量设置 |
| 互斥域 vs 跨池规则两个概念 | **合并为一个「互斥」概念**（见 §3.4） |

### 2.10 兼容策略

- **库文件**：新增 `axis` 作为容器层，旧 `categories/subcategories` 结构由迁移脚本一次性转换；
  过渡期保留双向读取（读旧结构 → 按映射表升格），写盘一律新结构。
- **`selection_state`**：`exclude_categories`（路径字符串）与 `fill_sub_ranges`（子类 id）需要迁移到
  轴/槽位引用；旧工作流加载时做一次内存迁移（沿用现有 `onConfigure` 自愈机制的做法）。
- **md 文件夹镜像**：见 §7 决策点 2。
- **`mark_synced` 指纹**：目录结构变了，首次启动必然触发一次 baseline 重建（预期内）。

## 3. UI 重设计

### 3.1 信息架构：按「使用频率」分层，而不是按「功能模块」并列

这是整个重写的第一原则。现状 8 页签的病根是**按功能模块并列**，导致低频功能寄居在高频入口里。

```
                    ┌─────────────────────────────────────────┐
   每次出图 (高频)   │  节点面板：选词 + 填充 + 预览            │   ← 常驻在画布上，必须极简
                    └─────────────────────────────────────────┘
                                     │ ➕ / ⋯
                    ┌─────────────────────────────────────────┐
   偶尔调 (中频)     │  挑选器：只做"选词"                      │   ← 弹窗，2 层结构压成 1 层
                    │  生成设置：模式/引擎/全局偏好             │   ← 小弹窗，从挑选器搬出来
                    └─────────────────────────────────────────┘
                                     │ 顶栏 🏷 / /taglib
                    ┌─────────────────────────────────────────┐
   几乎不调 (低频)   │  数据工作台：标签库 · 档案 · 互斥 · NL    │   ← 独立页面，可以做得厚
                    │  （全部可编辑，共用一套表格编辑器）        │
                    └─────────────────────────────────────────┘
```

姿势表**行内可编辑**：每行 = 一个姿势，字段用表单控件 ——

### 3.5 共用组件：`EntityTable`（一次解决三个页签）

这是"功能可以共用一套面板"的落地方式。三个数据页签本质相同：

```
EntityTable(schema)  →  列表 + 详情 + 行内编辑
  schema 描述: 实体名 / 主键 / 字段列表(名称·类型·是否必填·选项来源) / 子列表(嵌套的同类) / 校验
```

- 档案：实体=`profile`，子列表=`poses[]`
- 互斥域：实体=`group`，字段=`members`(标签多选)
- NL 句式：实体=`family`，子列表=`variants[]`（字符串列表）

同时保留统一的「原始 JSON」折叠入口（批量操作/粘贴时更快），但**默认走表单**。

- 互斥视图里点成员 → 跳到标签库

## 4. 交互原则（"可编辑优先"）

1. **默认可编辑，JSON 是逃生口**：每个数据视图第一屏就是表单/表格；JSON 折叠在「高级」里。
2. **局部保存 + 整体保存并存**：单条改完可立即存该条（走现有 `POST /api/profiles` 等接口，
   后端已经是"整树校验后落盘"，前端只需组装），失败时只标红出错那一条。
3. **改完即可预览**：档案/互斥/NL 的编辑结果能立刻跑一次 `/api/draw` 看效果（现有接口够用）。
4. **关系可导航**：任何实体引用（标签/轴/槽位）都可点进去。
5. **频率决定位置**：新功能默认先问"这多久用一次"，低频不进主面板。

| 22 | 抽到"带修饰词"却抽不到对应"基准词"时，语义漂移（只有 `thick thighs` 就永远是粗腿） | §1.6(一) | 覆盖统计 |
| 23 | **`total_max` 直接设默认值会系统性砍掉靠后的轴** | `engine.py:446` 的实现是「pinned/bundle 先留 → 其余按轴序截断」，`rest` 按 `order` 排序，所以靠后的 style / material / camera 会被**永远砍掉** —— 修一个缺陷会引入另一个 | 设 `total_max=60` 后统计各轴词数分布，看后段轴是否归零 |

**验证方式统一要求**：每个缺陷都要能写成一条**可复现的断言**进 §8.3 的重度测试，
不接受"看起来好了"。

### 8.2 新手体验：渐进披露

用户反馈"对初使用者上手难度非常高，详细页一眼看去就是一堆面板"。方案：

**一级 · 开箱即用（默认可见，≤5 个控件）**
节点面板只有：`模式（手动/自动）`、`🎲 填充`、`➕ 添加标签`、`预览`、`⋯`。
首次使用时给一条 3 步引导气泡（可永久关闭）：
① 点 🎲 直接出词 → ② 不满意就点 ➕ 挑词 → ③ 更多选项在 ⋯ 里。

**二级 · 进阶（⋯ 菜单 / 生成设置小弹窗）**
模式细节、引擎参数、显示语言、预览模式、UI 缩放。
每个控件配「人话说明 + 一个例子」，例如
`整体比例` → "100% = 默认；觉得字小就调到 115%"。

**三级 · 专家（数据工作台）**
标签库 / 档案 / 互斥 / NL —— 全部搬进独立页面（§3.4），
主流程里**不出现**这些概念，避免新手一眼看到 8 个陌生页签。

**其他降低门槛的措施**
| 措施 | 说明 |
|---|---|
| 预设（Presets） | 一键套用「纯标签 / 标签+自然语言 / 高质量堆词」等组合，不用理解内部参数 |
| 实时冲突提示 | 挑选器里选到互斥词时**当场标红并说明**（现在要等出图才发现） |
| 出词体检 | 填充后给一行摘要：`62 词 · 4 段 · ⚠️ 未发现冲突`（把 §8.3 的检查前移给用户看） |
| 危险操作确认 | 清空库 / 恢复备份 / 导入覆盖，二次确认并说明影响范围 |
| 错误可行动 | 报错不只给原因，给"下一步怎么做" |
| 术语统一 | 现在"轴/槽位/大类/子类/组/域/池"混用；统一为用户的词，不暴露内部实现术语 |

### 8.3 重度收尾验收测试（S9）

要求"高强度、重度"测试，确保出的词质量高、不冲突、顺序不乱。规格：

**T1 · 确定性**：同 seed 同配置 → 逐词完全相同（回归基线）。
**T2 · 万 seed 长跑（扩展 `m4 --long`）**：至少 10,000 seed，
对每轮输出断言：
- **互斥零共现**：年龄/情绪/表情/天气/时间/鞋类/取景/视角/风格基线，
  同维度内不得出现两个互斥值（当前每轮都有 → 必须归零）
- **人数一致性**：`1boy` 时不得出现 female 专属词；`1girl` 同理；`solo` 时不得出现互动词
- **数量分布**：输出词数落在 40~65（当前 200~213）
- **无畸形词**：输出中不得含 `xxx(yyy(zzz))` 形式
**T3 · 结构顺序**：输出必须严格符合所选顺序预设（Anima 六段 / Illustrious 末段式），
逐段校验位置正确。
**T4 · 覆盖率**：以群里那条基准提示词（62 词）为准，**≥95% 可在库内找到**
（当前 55%）；且每条"带修饰词"都有对应"基准词"。
**T5 · 别名**：常用同义/旧名（`tights` / `pantyhose` 等）能搜到且能去重。
**T6 · 冲突自检**：对同一配置的 200 个 seed 输出做两两交叉检查，
统计"同一轮内互斥共现率"，目标 0。
**T7 · 真实出图抽样**：随机抽 30 组输出，在 Anima 上实际出图，
人工（或 CLIP/美学模型）打分，确认**画面不自相矛盾**。这是最重也最不可省的一环。
**T8 · 多节点压力**：10 个节点同屏，渲染与轮询开销不随节点数线性劣化。
**T9 · 旧工作流兼容**：1.2.0 / 1.3.0 / 1.4.0 的工作流都能正常加载并出词。

> T1~T6、T9 可自动化进 `tools/run_gates.py`；**T7 必须人工**，作为发布前最后一道门。

## 参考依据（外部核对来源）

本方案的 §1.5 / §2.2~2.4 / §2.7 依据以下一手资料，非推测：

**Anima 提示词规范**（三处独立来源内容一致）
- Anima 官方模型页（Civitai）— tag order、正负向前缀、权重、tag dropout、Gelbooru 优先
- ComfyUI Wiki「Anima」条目 — 同上，含版本矩阵与采样参数
- 第三方实测教程（tungsten.run「CyberRealistic Anima」）— 明确「Anima 不是 CLIP/SDXL，
  Qwen 文本编码器读整句」，并单列 **style slot** 概念：`anime` / `anime screencap` /
  `realistic` / `@artist`，「换它就能换整体风格，其他不动」

**Danbooru 标签体系**（母数据集口径）
- `Help:Tags` / `Howto:Tag` — **5 个 category**：general(0) / artist(1) / copyright(3) /
  character(4) / meta(5)；以及标签命名规范：物体用单数、消歧用 `(qualifier)`、
  `_` 不能首尾、不得含逗号与星号
- `list of meta-wikis` — 官方 **Tag Group** 清单（约 100 个）
- `Tag group:image composition` — Styles / Techniques / Flaws / Quality / Background·Color
  同属一组；其中 Flaws 含 `Bad anatomy` / `Bad hands` / `Blurry` / `JPEG artifacts`，
  Quality 含 `Watermark` / `Resized` —— **负向提示词的词源**
- `Danbooru Tag Model`（DeepWiki）— Tag Alias / Tag Implication 机制

> 结论：Anima 的 tag order **就是 Danbooru 的 category 体系按生成需要重排**。
> 因此"分类逻辑对齐 Danbooru + Anima"不是外部强加，而是**回归母数据集与目标模型的口径**。
