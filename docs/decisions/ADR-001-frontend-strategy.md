# ADR-001: 前端重写策略 —— 分层渐进重写，且以门禁与行为基准为前置

> ⚠ **历史文档** —— 1.12.0 已删除 `.md` 镜像层（`data/default/taglib/` 现在只剩规则 .json），
> 文中「镜像目录 / 标签文件同步 / 单向删除 / 文件夹式存储」相关章节不再适用。
> 当前形态以 README.md 与 CHANGELOG.md 为准。


## Status

Accepted (2026-09-20)

## Context

`docs/UX-ARCHITECTURE-AUDIT-2026-09-20.md` 审查出 66 项缺陷，其中 UI 布局 20 项 + 交互逻辑 19 项，
绝大多数集中在三个巨型文件：`web/taglibrary.js`(1951) / `web/taglib-picker.js`(1868) / `web/manager.js`(1674)。

用户提出：不考虑成本前提下，是选「契约优先的收敛式整改」（原方案②）还是「前端推倒重写」（原方案③），
或者两者都选。

需要回答的核心问题不是"哪个便宜"，而是"两者是否存在依赖关系、能否组合、组合的正确形态是什么"。

## Decision

**两者都做，但必须串行，顺序不可颠倒；且③只能走"分层渐进重写"，禁止"一次性大爆炸重写"。**

### 1. 两者不是竞品，解决的是不同类问题

| 方案 | 解决的缺陷类型 | 不覆盖的部分 |
|---|---|---|
| ② 收敛式整改 | **同一语义多份实现**导致的行为漂移（镜像两路 / 文本三处 / 闸门两套 / 预设四份 / `escapeHtml` 五份） | 不改变"1951 行单文件"这个事实，下一轮迭代还会长出新的重复实现 |
| ③ 前端重写 | **文件过大**导致的缺陷密度与可维护性（双类冲突、死代码、定义两次的 CSS、五份 `escapeHtml` 都是"没人能看全一个文件"的症状） | 不修复后端的实现重复问题 |

因此不存在"哪个更好"，只存在执行顺序。

### 2. ③ 不能单独先行，理由不是成本，是三条硬约束

**2.1 没有安全网（最致命）**
前端 6438 行 JS 仅由 4 个**在线**门禁覆盖（`ui_v13_check` / `ui_theme_check` /
`ui_dialog_close_test` / `feature_e2e_test`），离线 `run_gates.py` 对前端 **0 覆盖**；
`manager.js`(1674 行) 的保存/导入/备份/恢复流程**无任何端到端门禁**。
在无回归保护下重写 7200 行，等于蒙眼拆房 —— 这不是"贵"，是"危险"。
② 建立的 6 条门禁正是这个安全网。

**2.2 序列化契约已进入用户工作流文件（破坏性风险）**
【复核】`nodes.py:95-99`：`selection_state` 是节点 **required STRING 输入**，
默认 `"{}"`，tooltip 写明"节点面板状态 (自动维护, 勿手改)"。
即用户已保存的工作流（本项目用户常见 19+ LoRA 的长工作流）里**已经存了完整面板状态**
（tags / exclude_categories / nsfw / gender / preview_mode / nsfw_intensity / total_min·max …）。
若重写改变 state 结构或字段名，用户打开老工作流会**静默丢失全部已选标签**，且无报错。

**2.3 宿主耦合是硬约束，不是可优化项**
插件 UI 不是独立 Web 应用，是嵌在 ComfyUI（litegraph 前端）里的三个视图：
节点面板必须挂到节点 DOM（实测同一 holder 存在 **3 份渲染克隆** `.taglib-panel`×3）、
高度依赖宿主变量 `--comfy-widget-height`、依赖 executed 回显、依赖 `translate="no"` 免疫浏览器翻译、
依赖 `serialize:false` 兜底。这些约束重写后**依然存在** —— 重写只能做到"内部模块化"，
做不到"解耦宿主"。

**2.4 会丢掉已查清的行级证据**
66 项缺陷的行号级定位是②的产物。它是③的**验收基准** ——
先有正确行为，再重写，才能做前后对比验证；凭记忆重写等于把已缴的学费再缴一遍。

### 3. ③ 的正确形态：分层重写，不是推倒重写

**保留（契约层，重写期间不许动）**

- `web/taglib-common.js` 状态层与**序列化契约**（对应 §2.2）
- 宿主适配层：节点 DOM 挂载、`--comfy-widget-height`、executed 回显、`translate="no"`、`serialize:false` 兜底
- CSS 变量真源 `.tl-scope`
- 全部 HTTP 接口契约（`/taglib/api/*` 32 个端点）

**重做（视图层）**

- 三个视图的组件结构：节点面板 / 挑选器（5 页签）/ 管理页
- 控件原语：开关 / 分段 / 下拉 / 按钮 **各一套实现**（避免 `.tl-sw`+`.tl-scene-btn` 双类冲突这类问题）
- 设计系统 token：圆角 / 间距 / 字号 / 语义色（并解决 `manager.css` 与 `.tl-scope` 两套变量漂移）
- **验收**：以②建立的 6 条门禁 + 现有 4 个 UI 门禁为断言集

### 4. 禁止"一次性大爆炸"，必须按视图/页签渐进

理由承 §2.2：用户在跑的 19+ LoRA 工作流不能被破坏。
推荐切分顺序（由外到内，风险递增）：

1. `manager.js`（独立页面，与节点面板零耦合，风险最低）
2. `taglib-picker.js` 的 5 个页签（彼此独立，天然边界）
3. `taglibrary.js` 节点面板（风险最高，放最后）

**每一步的放行条件**：`run_gates.py --with-online` 全绿 + 真机截图几何断言通过 +
打开一个**重写前保存的旧工作流**确认标签不丢。

真机验证按项目铁律走 huashu-chrome 接管用户自己的浏览器，**不得另起调试实例**。

### 5. 原批次 2（视觉布局）整体并入③

那 20 项视觉缺陷（`.tl-seg` 重复定义、开关双类冲突、浅色主题硬编码色、顶栏不换行、高度硬编码、
死代码、两套变量漂移）**几乎全部落在被重写的文件里** —— 单独修等于白做。

**例外**：保留 2~3 条「用户可感知且改动小于 5 行」的过渡补丁，避免用户长期忍受：

- 删掉 `tagpanel-css.js:216-225` 的重复 `.tl-seg` 定义（改 1 处修复 3 组控件选中态）
- 其余（含排除类目可见、🎲 可撤销）走阶段 B，作为③的行为基准

## Consequences

**正面**

- ③ 在门禁保护下进行，回归可被机械检出
- 阶段 B 修复的正确行为成为③的验收基准，避免"重写后行为反而退化"
- 批次 2 不重复投入，总工作量下降
- 契约层冻结 → 用户工作流兼容性有保障

**负面 / 风险**

- ③ 期间前端会有两套实现短暂共存（旧视图未拆完 + 新组件已就位），需明确"新组件只用于已迁移视图"
- 前端门禁需从"DOM 计数/几何"升级为"行为断言"，否则③的验收强度不足 —— 这是③开工前的**前置任务**
- ComfyUI 宿主前端持续演进（Vue 迁移等），③ 若绑定当前宿主细节，宿主升级会碎；
  因此验收必须走真机（huashu-chrome），不能只靠单测
